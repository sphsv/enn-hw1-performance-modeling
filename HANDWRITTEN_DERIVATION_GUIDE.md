# Подробный разбор решения и гайд для рукописной части

Этот документ объясняет решение сначала простыми словами, а затем формально.
Он нужен, чтобы разобраться в работе и подготовить обязательный рукописный
файл `hw1_handwritten.pdf`.

Сам Markdown-файл не заменяет рукописную работу. Итоговые формулы, основные
этапы вывода и предположения нужно разборчиво переписать от руки,
отсканировать или сфотографировать и объединить в один PDF.

## 1. Что требуется сделать

### Простыми словами

Есть небольшая свёрточная нейронная сеть. Размер картинки `S` и размер батча
`B` можно менять. Нужно заранее оценивать пять величин:

1. сколько вычислительных операций выполнит сеть;
2. сколько памяти потребуется во время прямого прохода;
3. сколько данных будет прочитано и записано;
4. сколько времени займёт прямой проход;
5. сколько энергии потратит GPU.

Первые три величины выводятся из архитектуры сети. Для времени и энергии одной
архитектуры недостаточно: одна и та же сеть работает по-разному на разных
GPU. Поэтому в формулах появляются параметры `θ`, которые подбираются по
реальным измерениям на конкретной видеокарте.

После подбора параметров модель проверяется на новых сочетаниях `(S, B)`,
которые не использовались при калибровке. Хорошая модель должна хотя бы
правильно описывать общий масштаб, переходы между режимами работы и границу
нехватки памяти. Идеального совпадения не ожидается.

### Терминами

Строится аналитическая модель производительности CNN в режиме inference:

- `FLOPs(S, B)` — число операций с плавающей точкой;
- `Memory(S, B)` — аналитический пик выделенной GPU-памяти;
- `BytesMoved(S, B)` — идеализированный объём трафика памяти;
- `Latency(S, B, θ)` — послойная roofline-модель задержки;
- `Energy(S, B, θ_E)` — линейная модель энергопотребления всего GPU.

Модель работает в FP32, в `eval()` и `torch.inference_mode()`. Один
multiply-accumulate считается за два FLOP.

## 2. Обозначения

| Обозначение | Смысл | Единица |
|---|---|---|
| `S` | высота и ширина квадратного изображения | пиксели |
| `B` | размер батча | изображения |
| `F_l` | число FLOPs оператора `l` | FLOP |
| `Q_l` | трафик памяти оператора `l` | байты |
| `t_launch` | эффективная цена запуска оператора | секунды |
| `P_eff` | эффективная вычислительная производительность | FLOP/s |
| `BW_eff` | эффективная пропускная способность памяти | байт/с |
| `e_launch` | энергия запуска одного оператора | джоули |
| `e_flop` | энергия одной вычислительной операции | джоуль/FLOP |
| `e_byte` | энергия перемещения одного байта | джоуль/байт |

По условию `S` всегда кратно 16. Поэтому после четырёх уменьшений размера в
два раза пространственные размеры остаются целыми.

## 3. Архитектура и формы тензоров

### Простыми словами

Свёртка с шагом `stride=2` уменьшает высоту и ширину примерно в два раза.
MaxPool с шагом 2 делает то же самое. Свёртка со `stride=1` сохраняет размер.

При этом число элементов зависит не только от высоты и ширины, но и от числа
каналов. Например, после первой свёртки форма равна
`B × 32 × S/2 × S/2`. Число элементов:

```text
B · 32 · (S/2) · (S/2) = 8 B S².
```

Именно такие выражения дальше используются в формулах FLOPs, памяти и трафика.

### Формально

Вход имеет форму `B × 3 × S × S`.

| Этап | Выходная форма | Число элементов |
|---|---|---:|
| Вход | `B × 3 × S × S` | `3 B S²` |
| Conv 7×7, stride 2, 3→32 | `B × 32 × S/2 × S/2` | `8 B S²` |
| ReLU + MaxPool 3×3, stride 2 | `B × 32 × S/4 × S/4` | `2 B S²` |
| Conv 5×5, 32→64 + ReLU | `B × 64 × S/4 × S/4` | `4 B S²` |
| Conv 3×3, stride 2, 64→128 + ReLU | `B × 128 × S/8 × S/8` | `2 B S²` |
| Conv 1×1, 128→256 + ReLU | `B × 256 × S/8 × S/8` | `4 B S²` |
| Conv 3×3, stride 2, 256→256 + ReLU | `B × 256 × S/16 × S/16` | `B S²` |
| Conv 1×1, 256→512 + ReLU | `B × 512 × S/16 × S/16` | `2 B S²` |
| Global Average Pooling | `B × 512` | `512 B` |
| Linear 512→256 + ReLU | `B × 256` | `256 B` |
| Linear 256→100 | `B × 100` | `100 B` |

BatchNorm в модели нет, потому что он отсутствует в архитектуре из задания.
У всех свёрток `bias=False`. У двух линейных слоёв смещения есть.

## 4. Число параметров

### Простыми словами

Параметры — это веса и смещения, которые постоянно хранятся на GPU. Их число
не зависит от `S` и `B`, но входит в формулы памяти и трафика.

У свёртки число весов равно:

```text
C_out · C_in · K².
```

У линейного слоя число параметров равно:

```text
N_in · N_out + N_out,
```

где второе слагаемое — смещение.

### Формально

| Слой | Расчёт | Параметры |
|---|---:|---:|
| Conv 7×7, 3→32 | `32·3·7²` | `4 704` |
| Conv 5×5, 32→64 | `64·32·5²` | `51 200` |
| Conv 3×3, 64→128 | `128·64·3²` | `73 728` |
| Conv 1×1, 128→256 | `256·128` | `32 768` |
| Conv 3×3, 256→256 | `256·256·3²` | `589 824` |
| Conv 1×1, 256→512 | `512·256` | `131 072` |
| Linear 512→256 | `512·256 + 256` | `131 328` |
| Linear 256→100 | `256·100 + 100` | `25 700` |

Итого:

```text
N_params = 1 040 324 параметра.
```

Все параметры хранятся в FP32, поэтому занимают:

```text
4 · 1 040 324 = 4 161 296 байт.
```

## 5. Вывод FLOPs

### Простыми словами

Каждое значение на выходе свёртки получается из большого числа умножений и
сложений. Сначала считаем работу для одного выходного элемента, затем умножаем
на число выходных элементов и размер батча.

По соглашению задания одно умножение с накоплением — это два FLOP: один FLOP
за умножение и один за сложение.

ReLU сравнивает число с нулём. MaxPool сравнивает девять значений окна 3×3 и
выбирает максимальное. Global Average Pooling складывает значения и делит
сумму на их количество.

### Формула для свёртки

Для квадратного ядра `K × K`:

```text
F_conv = 2 B H_out W_out C_out C_in K².
```

Здесь множитель 2 появляется из соглашения `1 MAC = 2 FLOP`.

### Шесть свёрток

```text
Conv 7×7, 3→32:
2 · B · (S/2)² · 32 · 3 · 7² = 2352 B S²

Conv 5×5, 32→64:
2 · B · (S/4)² · 64 · 32 · 5² = 6400 B S²

Conv 3×3, 64→128:
2 · B · (S/8)² · 128 · 64 · 3² = 2304 B S²

Conv 1×1, 128→256:
2 · B · (S/8)² · 256 · 128 = 1024 B S²

Conv 3×3, 256→256:
2 · B · (S/16)² · 256 · 256 · 3² = 4608 B S²

Conv 1×1, 256→512:
2 · B · (S/16)² · 512 · 256 = 1024 B S².
```

Суммарно:

```text
F_convs =
(2352 + 6400 + 2304 + 1024 + 4608 + 1024) B S²
= 17712 B S².
```

### ReLU, MaxPool и Global Average Pooling

Шесть ReLU после свёрток обрабатывают соответственно
`8 B S²`, `4 B S²`, `2 B S²`, `4 B S²`, `B S²` и `2 B S²` элементов:

```text
F_relu_conv = (8 + 4 + 2 + 4 + 1 + 2) B S² = 21 B S².
```

MaxPool создаёт `2 B S²` выходных элементов. Для выбора максимума из девяти
значений считаем восемь сравнений на один результат:

```text
F_pool = 8 · 2 B S² = 16 B S².
```

Это явное упрощающее предположение: на границах окна содержат padding, но для
закрытой формулы считаем одинаковую стоимость всех выходных элементов.

Global Average Pooling обрабатывает `2 B S²` входных элементов. Среднее из
`n` чисел требует `n−1` сложений и одного деления, то есть `n` операций:

```text
F_gap = 2 B S².
```

### Классификатор

Первая линейная операция, её смещение и ReLU, затем вторая линейная операция
и её смещение дают:

```text
F_classifier =
2·512·256·B + 256B + 256B + 2·256·100·B + 100B
= 313956 B.
```

### Итоговая формула FLOPs

```text
FLOPs(S,B) =
17712 B S² + 21 B S² + 16 B S² + 2 B S² + 313956 B

FLOPs(S,B) = B (17751 S² + 313956).
```

## 6. Вывод пиковой памяти

### Простыми словами

Пиковая память — это не сумма размеров всех промежуточных тензоров. После
завершения слоя старые промежуточные результаты могут быть освобождены и их
память используется снова.

Нужно найти момент, когда одновременно живёт самый большой набор тензоров.
Исходный вход остаётся в памяти, потому что им владеет вызывающий код. Во время
операции также одновременно существуют вход и выход текущего слоя.

Самый большой набор возникает во время первого MaxPool:

- исходный вход: `3 B S²` элементов;
- вход MaxPool, то есть выход первой свёртки: `8 B S²`;
- создаваемый выход MaxPool: `2 B S²`.

Всего получается `13 B S²` элементов активаций.

### Формально

FP32 занимает четыре байта. Параметры модели и максимальный набор активаций
дают:

```text
Memory(S,B) = 4 (N_params + 13 B S²)

Memory(S,B) = 4 (1 040 324 + 13 B S²) байт.
```

### Что формула не учитывает

Это намеренно простая аналитическая оценка. Она не включает:

- временную рабочую память алгоритмов cuDNN;
- округление размеров CUDA-аллокатором;
- кэшированную, но уже не занятую тензорами память;
- CUDA context и память других процессов;
- внутренние буферы библиотек.

В эксперименте измеряется `torch.cuda.max_memory_allocated()`, то есть именно
активно выделенная PyTorch память. Даже эта величина может быть больше формулы
из-за скрытых рабочих тензоров. Поэтому расхождение — часть анализа, а не
автоматически ошибка кода.

## 7. Вывод объёма перемещённых данных

### Простыми словами

Память отвечает на вопрос «сколько данных одновременно лежит на GPU», а
`BytesMoved` — «сколько данных суммарно прочитали и записали все операции».

Один и тот же тензор может много раз участвовать в разных операциях. Поэтому
суммарный трафик обычно намного больше пикового объёма памяти.

Для каждого оператора предполагаем:

1. вход читается один раз;
2. веса и смещения читаются один раз;
3. выход записывается один раз.

Кэши и fusion не учитываются. ReLU работает на месте, но всё равно читает и
записывает активацию.

### Формально

Коэффициенты при `B S²` для 14 пространственных операций:

```text
Conv1:   3 + 8 = 11
ReLU1:   8 + 8 = 16
MaxPool: 8 + 2 = 10
Conv2:   2 + 4 = 6
ReLU2:   4 + 4 = 8
Conv3:   4 + 2 = 6
ReLU3:   2 + 2 = 4
Conv4:   2 + 4 = 6
ReLU4:   4 + 4 = 8
Conv5:   4 + 1 = 5
ReLU5:   1 + 1 = 2
Conv6:   1 + 2 = 3
ReLU6:   2 + 2 = 4
GAP input:       2
------------------
Итого:          91 B S² элементов.
```

После Global Average Pooling остаются части, зависящие от `B`, но не от `S`:

```text
GAP output:                512 B
Linear1 input + output:    512 B + 256 B = 768 B
ReLU input + output:       256 B + 256 B = 512 B
Linear2 input + output:    256 B + 100 B = 356 B
------------------------------------------------
Итого:                    2148 B элементов.
```

Все веса и смещения вместе дают `1 040 324` элемента. После умножения на
четыре байта FP32:

```text
BytesMoved(S,B) =
4 (91 B S² + 2148 B + 1 040 324) байт.
```

## 8. Модель задержки

### Простыми словами

Операция на GPU может быть медленной по трём разным причинам:

1. сама работа слишком маленькая, и основную долю времени занимает запуск;
2. вычислительных операций мало, но нужно прочитать и записать много данных;
3. арифметики настолько много, что ограничением становятся вычислительные
   блоки GPU.

Для каждого слоя отдельно оцениваем время вычислений и время передачи данных.
Если GPU способен частично выполнять их параллельно, время слоя определяется
большей из двух величин. Затем добавляется цена запуска, а времена всех слоёв
складываются, потому что сеть последовательная.

### Терминами

Используется послойная roofline-модель с параметрами:

```text
θ = (t_launch, P_eff, BW_eff).
```

Для оператора `l`:

```text
t_compute,l = F_l / P_eff,
t_memory,l  = Q_l / BW_eff,
t_l = t_launch + max(t_compute,l, t_memory,l).
```

Для всей сети:

```text
Latency(S,B; θ) =
Σ_l [t_launch + max(F_l(S,B)/P_eff, Q_l(S,B)/BW_eff)].
```

В модели 17 концептуальных операторов:

```text
6 Conv + 7 ReLU + 1 MaxPool + 1 GAP + 2 Linear = 17.
```

Седьмой ReLU находится между двумя линейными слоями. `Flatten` является только
изменением представления тензора и отдельным вычислительным оператором не
считается.

Параметры называются эффективными, потому что они не обязаны совпадать с
паспортными характеристиками GPU. Они поглощают реальные накладные расходы,
неидеальную загрузку устройства, выбор CUDA-ядер и другие эффекты.

### Как параметры калибруются

На базовой сетке измеряется настоящая задержка. Затем подбираются положительные
`t_launch`, `P_eff` и `BW_eff`, минимизирующие разницу между измерением и
предсказанием.

В `calibrate.py` минимизируется разница логарифмов:

```text
log(Latency_pred) − log(Latency_real).
```

Так маленькие и большие конфигурации получают более сопоставимый вес. Если бы
минимизировалась обычная абсолютная ошибка, самые долгие точки почти полностью
определяли бы результат.

## 9. Модель энергии

### Простыми словами

Энергия — это мощность, накопленная за время работы. В простой модели считаем,
что энергия складывается из трёх частей:

- постоянная цена запусков операторов;
- цена вычислений;
- цена перемещения данных.

Чем больше FLOPs и трафика, тем больше ожидаемая энергия.

### Формально

```text
Energy(S,B; θ_E) =
17 e_launch
+ e_flop FLOPs(S,B)
+ e_byte BytesMoved(S,B).
```

Здесь:

```text
θ_E = (e_launch, e_flop, e_byte).
```

Коэффициенты подбираются методом неотрицательных наименьших квадратов. Они не
могут быть отрицательными, потому что отрицательная стоимость вычисления или
перемещения байта не имеет физического смысла.

Энергия измеряется для всего GPU без вычитания энергопотребления в простое.
Если видеокарта поддерживает накопительный счётчик NVML, используется разница
его показаний до и после серии forward pass. Иначе мощность регулярно
считывается через NVML и интегрируется по времени.

Это феноменологическая, а не точная физическая модель. Она явно не описывает:

- DVFS — динамическое изменение частот и напряжения;
- нагрев и температурный throttling;
- фоновую нагрузку других процессов;
- дискретность датчиков энергии и мощности;
- различия энергопотребления отдельных типов CUDA-ядер.

## 10. Пример расчёта

Возьмём `S = 224` и `B = 8`.

### FLOPs

```text
FLOPs(224,8) = 8 · (17751 · 224² + 313956)
= 7 127 905 056 FLOP
≈ 7.128 GFLOP.
```

### Аналитическая память

```text
Memory(224,8) = 4 · (1 040 324 + 13 · 8 · 224²)
= 25 034 512 байт
≈ 23.875 MiB.
```

### Трафик

```text
BytesMoved(224,8) =
4 · (91 · 8 · 224² + 2148 · 8 + 1 040 324)
= 150 342 544 байт
≈ 143.378 MiB.
```

Задержку и энергию нельзя получить числом, пока не известны параметры,
откалиброванные на выбранном GPU.

## 11. Сетка измерений и разделение данных

### Простыми словами

Сначала измеряем много разных размеров изображений и батчей. Часть точек
используем, чтобы настроить модель, а остальные прячем от калибровки и потом
проверяем на них качество предсказаний.

Это важно: хорошее совпадение на тех же точках, по которым подбирались
параметры, ещё не доказывает, что формула умеет предсказывать новые случаи.

### Формально

Базовые значения:

```text
S = 32, 64, 128, 224, 256, 384, 512
B = 1, 2, 4, 8, 16, 32, 64, 128, 256.
```

При seed 7 случайно выбраны:

```text
S_random = 144, 272, 304, 448
B_random = 18, 24, 219.
```

Всего:

```text
11 размеров · 12 батчей = 132 конфигурации.
```

Разделение:

- 63 точки `base S × base B` — calibration;
- 69 точек, где `S` или `B` случайный, — validation.

Если калибровочная конфигурация завершилась OOM, она записывается в CSV, но не
может использоваться для подбора latency и energy, потому что успешного
измерения нет.

Порядок 132 конфигураций перемешивается. Это уменьшает риск, что все тяжёлые
точки окажутся в конце и систематически измерятся на более горячем GPU.

## 12. Как выполняются реальные измерения

Перед всеми измерениями устанавливаются одинаковые настройки:

```python
torch.backends.cudnn.benchmark = False
torch.backends.cudnn.allow_tf32 = False
torch.backends.cuda.matmul.allow_tf32 = False
model = model.cuda().eval()
```

### Latency

1. Выполняются прогревочные forward pass.
2. Один пробный запуск оценивает длительность.
3. Число повторов автоматически выбирается так, чтобы измерение было
   достаточно длинным, но не чрезмерным.
4. Каждый forward окружается CUDA events.
5. После синхронизации берётся медиана отдельных измерений.

Медиана устойчивее среднего к редким выбросам от фоновых процессов и
инициализации библиотек.

### Peak memory

1. Очищается неиспользуемый CUDA cache.
2. Сбрасывается статистика пика.
3. Выполняется один forward в `torch.inference_mode()`.
4. Читается `torch.cuda.max_memory_allocated()`.

### Energy

Forward повторяется примерно в течение одной секунды. Более длинное окно
нужно, потому что датчик энергии имеет ограниченную частоту и разрешение.
Общая энергия серии делится на число forward pass.

### OOM

`torch.cuda.OutOfMemoryError` перехватывается. В строке CSV сохраняются `S`,
`B`, статус `OOM` и аналитическое предсказание памяти. После этого временные
объекты освобождаются, cache очищается, и измерения продолжаются.

## 13. Как читать графики и метрики

### Поверхности latency, memory и energy

Цветная поверхность — аналитическое предсказание. Точки — реальные измерения.
Чем ближе точки к поверхности, тем лучше модель описывает данные.

На графике памяти OOM-конфигурации отмечены красными крестами на высоте
предсказанной памяти. Так видно, была ли аналитическая граница слишком
оптимистичной.

### Predicted versus measured

По горизонтали находится измеренное значение, по вертикали — предсказанное.
Идеальная модель лежит на диагонали `y = x`.

- точки выше диагонали: модель завышает значение;
- точки ниже диагонали: модель занижает значение;
- calibration и validation показаны разными маркерами.

### Режимы latency

Для каждой точки сравниваются три вклада:

- `launch` — накладные расходы запуска;
- `memory` — ограничение пропускной способностью памяти;
- `compute` — ограничение вычислительной производительностью.

Ожидаемая картина:

- маленькие `S` и `B` чаще launch-bound;
- операции с низкой арифметической интенсивностью могут быть memory-bound;
- крупные свёртки при больших `S` и `B` чаще compute-bound.

### Метрики

- `MAE` — средняя абсолютная ошибка в исходных единицах;
- `RMSE` — сильнее штрафует крупные ошибки;
- `MAPE` — средняя относительная ошибка в процентах;
- `Median APE` — медианная относительная ошибка, устойчивая к выбросам;
- `R²` — доля объяснённой вариации; значение ближе к 1 обычно лучше.

Главное качество нужно оценивать на validation, а не только на calibration.

## 14. Почему формулы не совпадут с измерениями идеально

### Latency

- разные свёртки запускают разные CUDA-ядра;
- один общий `P_eff` не описывает все размеры и формы тензоров;
- cuDNN использует эвристики выбора алгоритма;
- реальные ядра могут быть разбиты или объединены иначе, чем 17 операторов;
- кэширование уменьшает часть трафика;
- частота GPU меняется из-за DVFS и температуры.

### Memory

- cuDNN может запросить workspace;
- CUDA-аллокатор округляет размеры блоков;
- аналитическая формула не учитывает внутренние буферы;
- OOM зависит не только от `max_memory_allocated()`, но и от фрагментации и
  доступной памяти устройства.

### Energy

- датчики имеют ограниченную точность;
- часть энергии тратится даже в простое;
- мощность зависит от температуры и частоты;
- короткие операции трудно измерять по отдельности;
- фоновые процессы используют тот же GPU.

Именно эти расхождения нужно обсуждать в README после финального запуска.
