# Часть 1. Что просит задание

## 1.1. Суть задания простыми словами

Дана небольшая свёрточная нейронная сеть. На её вход подаётся батч из `B`
квадратных картинок размером `S × S`.

Нужно научиться заранее оценивать:

1. сколько вычислений сделает сеть;
2. сколько GPU-памяти ей понадобится;
3. сколько времени займёт один прямой проход;
4. сколько энергии потратит GPU.

Для этого требуется:

- вывести формулы на бумаге;
- реализовать формулы в Python;
- измерить настоящую сеть на GPU;
- подобрать неизвестные параметры времени и энергии;
- проверить формулы на новых значениях `S` и `B`;
- построить графики и объяснить расхождения.

## 1.2. Какие функции нужно получить

По условию нужны четыре функции:

```python
flops(image_size, batch)
memory(image_size, batch)
latency(image_size, batch, theta)
energy(image_size, batch, theta_energy)
```

Дополнительно нужна величина `BytesMoved(S,B)`, потому что объём перемещённых
данных используется в моделях latency и energy.

| Функция | Что она отвечает | Нужно калибровать на GPU? |
|---|---|---|
| `FLOPs(S,B)` | сколько вычислительных операций выполнено | нет |
| `Memory(S,B)` | какой аналитический пик памяти ожидается | нет |
| `Latency(S,B,θ)` | сколько секунд займёт forward pass | да |
| `Energy(S,B,θ_E)` | сколько джоулей потратит GPU | да |

## 1.3. Что означает «калибровать»

Архитектура позволяет точно посчитать число операций и размеры тензоров. Но
по одной архитектуре нельзя узнать реальное время и энергию: они зависят от
конкретной видеокарты.

Поэтому:

1. запускаем сеть на GPU;
2. измеряем настоящие latency и energy;
3. подбираем параметры формул так, чтобы предсказания были близки к
   измерениям;
4. проверяем параметры на точках, которые не участвовали в подборе.

Это и называется калибровкой модели.

## 1.4. На каких значениях нужно измерять

Базовые размеры изображения:

```text
S = 32, 64, 128, 224, 256, 384, 512.
```

Базовые размеры батча:

```text
B = 1, 2, 4, 8, 16, 32, 64, 128, 256.
```

К ним добавляются:

- 4 случайных размера изображения, кратных 16;
- 3 случайных размера батча, не являющихся степенями двойки.

Итого должно быть:

```text

```

Если конфигурация не помещается в память, программа не должна падать. Нужно
записать её со статусом `OOM` и продолжить измерения.

## 1.5. На какой видеокарте нужно запускать

Итоговые измерения должны быть выполнены на одной недорогой NVIDIA GPU:

- Tesla T4;
- Tesla P100;
- либо локальной NVIDIA GPU с памятью не более 16 ГБ.

A100 80 ГБ не подходит для финальных результатов. На ней можно проверять код,
но нельзя выдавать эти измерения за итог эксперимента.

# Часть 3. Объяснение решения

## 3.1. Архитектура сети

### Простыми словами

Свёртки извлекают признаки из изображения. Некоторые слои уменьшают высоту и
ширину в два раза. В конце Global Average Pooling превращает каждую карту
признаков в одно число, а два линейных слоя выдают 100 классов.

### Формы тензоров

Вход имеет форму `B × 3 × S × S`, где `S` делится на 16.

| Этап | Выход | Число элементов |
|---|---|---:|
| Вход | `B × 3 × S × S` | `3 B S²` |
| Conv 7×7, stride 2, 3→32 | `B × 32 × S/2 × S/2` | `8 B S²` |
| MaxPool 3×3, stride 2 | `B × 32 × S/4 × S/4` | `2 B S²` |
| Conv 5×5, 32→64 | `B × 64 × S/4 × S/4` | `4 B S²` |
| Conv 3×3, stride 2, 64→128 | `B × 128 × S/8 × S/8` | `2 B S²` |
| Conv 1×1, 128→256 | `B × 256 × S/8 × S/8` | `4 B S²` |
| Conv 3×3, stride 2, 256→256 | `B × 256 × S/16 × S/16` | `B S²` |
| Conv 1×1, 256→512 | `B × 512 × S/16 × S/16` | `2 B S²` |
| Global Average Pooling | `B × 512` | `512 B` |
| Linear 512→256 | `B × 256` | `256 B` |
| Linear 256→100 | `B × 100` | `100 B` |

После каждой свёртки стоит ReLU. Ещё один ReLU расположен между линейными
слоями. BatchNorm нет, потому что его нет в архитектуре задания.

## 3.2. Откуда взялось число параметров

### Простыми словами

У свёртки число весов зависит от количества входных каналов, выходных каналов
и размера ядра:

```text
C_out · C_in · K².
```

У линейного слоя:

```text
N_in · N_out + N_out,
```

где `N_out` в конце — смещение.

### Расчёт

```text
Conv 7×7:      32·3·7²          =   4 704
Conv 5×5:      64·32·5²         =  51 200
Conv 3×3:      128·64·3²        =  73 728
Conv 1×1:      256·128          =  32 768
Conv 3×3:      256·256·3²       = 589 824
Conv 1×1:      512·256          = 131 072
Linear 512→256: 512·256 + 256   = 131 328
Linear 256→100: 256·100 + 100   =  25 700
------------------------------------------------
Итого:                              1 040 324
```

Свёртки не имеют смещений: в условии задано `bias=False`.

## 3.3. Как получена формула FLOPs

### Простыми словами

Каждый выходной элемент свёртки требует много умножений и сложений. Считаем
работу для одного элемента, умножаем на число выходных элементов и на батч.

По условию:

```text
1 multiply-accumulate = 2 FLOP.
```

### Формула одной свёртки

```text
F_conv = 2 B H_out W_out C_out C_in K².
```

### Вклад шести свёрток

```text
Conv 7×7, 3→32:       2352 B S²
Conv 5×5, 32→64:      6400 B S²
Conv 3×3, 64→128:     2304 B S²
Conv 1×1, 128→256:    1024 B S²
Conv 3×3, 256→256:    4608 B S²
Conv 1×1, 256→512:    1024 B S²
--------------------------------
Все свёртки:         17712 B S²
```

Например, первая свёртка:

```text
2 · B · (S/2)² · 32 · 3 · 7² = 2352 B S².
```

### Остальные операции

ReLU выполняет одно сравнение для каждого элемента:

```text
F_relu = (8 + 4 + 2 + 4 + 1 + 2) B S²
= 21 B S².
```

MaxPool 3×3 создаёт `2 B S²` результатов. Для выбора максимума из девяти
значений считаем восемь сравнений:

```text
F_pool = 8 · 2 B S² = 16 B S².
```

Global Average Pooling требует `n−1` сложений и одно деление для `n` чисел:

```text
F_gap = 2 B S².
```

Два линейных слоя, их смещения и ReLU между ними:

```text
F_classifier =
2·512·256·B + 256B + 256B + 2·256·100·B + 100B
= 313956 B.
```

### Итог

```text
FLOPs(S,B) =
17712 B S² + 21 B S² + 16 B S² + 2 B S² + 313956 B

FLOPs(S,B) = B (17751 S² + 313956).
```

## 3.4. Как получена формула памяти

### Простыми словами

Не нужно складывать размеры всех тензоров сети. Промежуточные результаты
освобождаются по мере выполнения. Нужно найти момент, когда одновременно
существует больше всего данных.

Самый большой набор возникает во время первого MaxPool:

```text
исходный вход:          3 B S²
выход первой свёртки:   8 B S²
создаваемый MaxPool:    2 B S²
--------------------------------
всего:                 13 B S² элементов
```

Исходный вход остаётся жив, потому что им владеет вызывающий код. Параметры
модели тоже постоянно находятся в памяти.

### Формально

Одно число FP32 занимает четыре байта:

```text
Memory(S,B) = 4 (1 040 324 + 13 B S²) байт.
```

Это аналитическая оценка. Она не учитывает:

- workspace cuDNN;
- округление CUDA-аллокатора;
- внутренние буферы библиотек;
- память других процессов;
- фрагментацию памяти.

Поэтому настоящий OOM может произойти раньше, чем предсказывает формула.

## 3.5. Как получена формула BytesMoved

### Простыми словами

`Memory` отвечает на вопрос «сколько данных одновременно лежит в памяти».
`BytesMoved` отвечает на другой вопрос: «сколько данных все слои суммарно
прочитали и записали».

Один тензор может читаться несколькими операциями, поэтому трафик обычно
больше пикового объёма памяти.

Предполагаем, что каждый оператор:

1. один раз читает вход;
2. один раз читает веса и смещения;
3. один раз записывает выход.

Кэширование и fusion не учитываются. In-place ReLU использует ту же память,
но всё равно читает и записывает значения.

### Сумма пространственных частей

```text
Conv1:   3 + 8 = 11
ReLU1:   8 + 8 = 16
MaxPool: 8 + 2 = 10
Conv2:   2 + 4 = 6
ReLU2:   4 + 4 = 8
Conv3:   4 + 2 = 6
ReLU3:   2 + 2 = 4
Conv4:   2 + 4 = 6
ReLU4:   4 + 4 = 8
Conv5:   4 + 1 = 5
ReLU5:   1 + 1 = 2
Conv6:   1 + 2 = 3
ReLU6:   2 + 2 = 4
GAP input:       2
------------------
Итого:          91 B S² элементов
```

### Части, не зависящие от S

```text
GAP output:                 512 B
Linear1 input и output:     768 B
ReLU input и output:        512 B
Linear2 input и output:     356 B
---------------------------------
Итого:                     2148 B элементов
```

Все веса и смещения дают ещё `1 040 324` элемента. Умножаем всё на четыре
байта:

```text
BytesMoved(S,B) =
4 (91 B S² + 2148 B + 1 040 324) байт.
```

## 3.6. Как устроена модель latency

### Простыми словами

Операция на GPU может быть медленной по трём причинам:

1. операция маленькая, а запуск CUDA-ядра занимает заметное время;
2. нужно перемещать много данных — ограничением становится память;
3. нужно выполнять много арифметики — ограничением становятся вычислительные
   блоки GPU.

Для каждого слоя считаем время вычислений и время передачи данных. Берём
большее из них и добавляем стоимость запуска. Потом складываем времена слоёв.

### Терминами

Параметры модели:

```text
θ = (t_launch, P_eff, BW_eff),
```

где:

- `t_launch` — эффективная цена запуска оператора, секунд;
- `P_eff` — эффективная производительность, FLOP/s;
- `BW_eff` — эффективная пропускная способность, байт/с.

Для слоя `l`:

```text
t_compute,l = F_l / P_eff
t_memory,l  = Q_l / BW_eff
```

Итоговая roofline-модель:

```text
Latency(S,B;θ) =
Σ_l [t_launch + max(F_l(S,B)/P_eff, Q_l(S,B)/BW_eff)].
```

Используются 17 концептуальных операторов:

```text
6 Conv + 7 ReLU + 1 MaxPool + 1 GAP + 2 Linear = 17.
```

`Flatten` не выполняет вычислений: он только меняет представление тензора.

## 3.7. Как устроена модель energy

### Простыми словами

Энергия складывается из:

- стоимости запусков;
- стоимости арифметики;
- стоимости перемещения данных.

### Формально

```text
Energy(S,B;θ_E) =
17 e_launch
+ e_flop FLOPs(S,B)
+ e_byte BytesMoved(S,B).
```

Параметры:

- `e_launch` — джоули на запуск;
- `e_flop` — джоули на FLOP;
- `e_byte` — джоули на байт.

Коэффициенты ограничены снизу нулём, потому что отрицательная стоимость
операции физически не имеет смысла.

Энергия измеряется для всего GPU без вычитания idle power. Модель не учитывает
нагрев, DVFS, фоновые процессы и дискретность датчиков.

## 3.8. Как выполняется калибровка и проверка

При seed 7 случайно выбраны:

```text
S_random = 144, 272, 304, 448
B_random = 18, 24, 219.
```

Разделение данных:

```text
63 точки base S × base B         → calibration
69 точек со случайным S или B    → validation
```

На calibration подбираются `θ` и `θ_E`. На validation параметры уже не
меняются — только оценивается ошибка.

Для latency минимизируется разница логарифмов предсказания и измерения. Это
не позволяет самым долгим конфигурациям полностью подавить короткие.

Для energy используется non-negative least squares — метод наименьших
квадратов с неотрицательными коэффициентами.

## 3.9. Как выполняются измерения

Обязательные настройки:

```python
torch.backends.cudnn.benchmark = False
torch.backends.cudnn.allow_tf32 = False
torch.backends.cuda.matmul.allow_tf32 = False
model = model.cuda().eval()
```

Все forward pass выполняются в `torch.inference_mode()` и FP32.

### Latency

- несколько прогревочных запусков;
- CUDA events вокруг каждого forward pass;
- синхронизация GPU;
- медиана повторов.

### Memory

- сброс статистики пика;
- один forward pass;
- чтение `torch.cuda.max_memory_allocated()`.

### Energy

- forward повторяется примерно одну секунду;
- читается NVML cumulative energy;
- если счётчик не поддерживается, интегрируется NVML power;
- энергия серии делится на число повторов.

### OOM

`torch.cuda.OutOfMemoryError` перехватывается. Конфигурация сохраняется со
статусом `OOM`, память освобождается, измерения продолжаются.

## 3.10. Что должны показать графики

### Surface plot

Цветная поверхность — предсказание формулы. Точки — настоящие измерения.

### Predicted versus measured

Идеальные точки лежат на диагонали `y=x`:

- выше диагонали — модель завышает;
- ниже диагонали — модель занижает.

Calibration и validation показаны разными маркерами.

### Режимы latency

- `launch-bound` — доминирует запуск;
- `memory-bound` — доминирует передача данных;
- `compute-bound` — доминируют вычисления.

Обычно маленькие задачи launch-bound, слои с низкой арифметической
интенсивностью memory-bound, а крупные свёртки compute-bound.


Численные значения `θ` будут получены после калибровки на T4/P100.

## 4.7. Energy

```text
Energy(S,B;θ_E) =
17 e_launch
+ e_flop FLOPs(S,B)
+ e_byte BytesMoved(S,B).
```

```text
θ_E = (e_launch, e_flop, e_byte).
```

Численные значения `θ_E` будут получены после измерений энергии на T4/P100.

## 4.8. Числовой пример

Для `S=224`, `B=8`:

```text
FLOPs = 7 127 905 056 FLOP ≈ 7.128 GFLOP

Memory = 25 034 512 байт ≈ 23.875 MiB

BytesMoved = 150 342 544 байт ≈ 143.378 MiB
```

Latency и Energy пока нельзя честно подставить числа: без финального запуска
на подходящей GPU такие значения пришлось бы выдумать.

## 4.9. Главный вывод

Мы получили закрытые формулы FLOPs, аналитической памяти и трафика. Для
latency и energy получены параметрические модели. После одного запуска
`measure.py` на T4/P100 код автоматически соберёт данные, `calibrate.py`
подберёт неизвестные параметры, а `plots.py` построит требуемые графики.
